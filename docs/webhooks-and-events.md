# Webhooks and Events

## Tenant System to Billing

Billing offers a REST API and a mechanism for receiving Events from the Tenant System. Integrated operations:

- Customer Mapping
- Pricing and Cost Estimation
- Reservation
- Usage Metering
- Charge
- Refund Request, if authorized
- Related business Events

## Billing to Tenant System

Billing proactively sends Webhooks when business state changes.

| Event | Meaning |
|---|---|
| `reservation.created` | A Reservation was created |
| `reservation.expired` | A Reservation expired |
| `reservation.released` | A Reservation was released |
| `charge.succeeded` | A Charge succeeded |
| `charge.failed` | A Charge failed |
| `payment.succeeded` | A Payment succeeded |
| `payment.failed` | A Payment failed |
| `refund.succeeded` | A Refund succeeded |
| `invoice.created` | An Invoice was created |
| `invoice.paid` | An Invoice was paid |
| `subscription.renewed` | A Subscription was renewed |
| `subscription.payment_failed` | A Subscription payment failed |

This table is the specification's example list and is not complete. The event schemas in [contracts/events](../contracts/events/README.md) now own the event list and the shape of each event's `data`; the application reads the type list from them and rejects a subscription to a type that has no schema.

## Principles

- A Webhook only reflects a business state or result.
- Events are never used to impose an action on the Tenant System.
- The Tenant System defines its own policy for handling Events. For example, on `payment.failed` it may record a debt, extend the payment period, suspend the Resource, or keep providing the service. Billing does not decide for it.
- Supports Retry, Signature Verification and Idempotency.
- Outbound Webhooks are signed with HMAC-SHA256 over the timestamp and the raw request body, carry the timestamp and a key id, reject a stale timestamp, and process an event id once. The signing secret is separate from the API credential a Tenant System uses to call Billing.
- Keeps delivery history and processing status, and supports resending a Webhook.
- A Tenant configures its Webhook Endpoints and the Event types it wants to receive.

## Delivery

- Every event is written to the outbox in the same transaction as the change it reports. A relay moves it to in-process consumers; the webhook consumer queues one delivery per subscribed endpoint of the event's Tenant, holding the exact body that will be signed.
- The sender claims due deliveries without blocking other workers, posts them, and records every attempt (status, latency, a short excerpt of the response). Success is any 2xx. Failures retry with exponential backoff and jitter up to a bounded number of attempts, then the delivery is `DEAD`: kept, visible, and resendable.
- A worker that dies mid-send loses nothing: its claim is a lease, and the delivery becomes due again when the lease runs out. Delivery is at-least-once and unordered, so receivers deduplicate on `Billing-Event-Id`.
- A Tenant-chosen URL is untrusted, so the sender refuses non-public destinations and checks them inside the connection's own DNS resolution; a changed DNS answer cannot slip past a check made earlier. The rule and its enforcement are in [security-and-reliability.md](security-and-reliability.md).
- The signing secret is generated by Billing, shown once, stored encrypted (see [security-and-reliability.md](security-and-reliability.md)) and replaced by rotation. Headers, signature format and a verification recipe in Java and TypeScript are in [contracts/events/README.md](../contracts/events/README.md).
- Switching the sender off with `billing.webhooks.sender-enabled=false` is the rollback: deliveries stay queued and go out when it is switched back on.

### Latency budget

From a committed event to a receiver's answer, a healthy delivery spends at most `billing.outbox.poll-delay` (1s)
until the relay sees the event, one consumer transaction to queue the delivery, `billing.webhooks.poll-delay` (1s)
until the sender picks it up, and then the HTTP call. The outbound HTTP limits are
`billing.webhooks.max-connections` (100) and `max-connections-per-route` (25); a send waits at most
`connection-request-timeout` (2s) for a pooled connection, then `connect-timeout` (3s) and `read-timeout` (10s).
Their sum must stay within `billing.webhooks.deadline` (15s), so a saturated pool fails fast with `timeout` instead
of holding a worker for the read timeout. `billing.webhook.lag` is a timer with one sample per successful delivery,
measured from the delivery row's creation to the completed attempt; it therefore excludes the outbox poll delay and
the consumer transaction, and the end-to-end number is the load test's.

Reliability mechanics (outbox, backoff, dead-letter queue, idempotent consumers) are in [security-and-reliability.md](security-and-reliability.md). Inbound Stripe webhooks are in [payments-and-stripe.md](payments-and-stripe.md).
